# MLOps_S26: Deep Technical Audit Report

**Scope:** Full repository analysis (including `main` and `feature/*` branches)
**Status:** Complete
**Date:** April 14, 2026

## Overview
Данный отчет представляет собой глубокий технический аудит архитектуры и реализации системы MLOps_S26. Анализ проводился на основе изучения исходного кода, схем миграций базы данных, конфигураций Docker и пайплайнов обучения. 

*Примечание: Основная логика автоматизации реализована в ветке `feature/training-worker`.*

---

### 1. Как сервисы общаются между собой?
**Статус:** [IMPLEMENTED]  
**Детали:** Система использует гибридную модель:
* **Асинхронная через общую БД (Shared Database Pattern):** Основной механизм передачи состояний задач (таблицы `jobs`, `trained_models`) и логирования (`prediction_logs`). Это обеспечивает слабую связность компонентов.
* **Синхронная через REST API:** Используется для управления жизненным циклом (запросы к `orchestrator`) и для получения предсказаний в реальном времени (`inference-service`).
* **Общие инфраструктурные сервисы:** Все компоненты подключены к единым инстансам `PostgreSQL`, `MinIO` и `MLflow`.

### 2. Как один сервис узнает адрес другого?
**Статус:** [IMPLEMENTED]  
**Детали:** Используются **Docker service names** (например, `postgres`, `minio`, `mlflow`), определенные в `docker-compose.yml`. Это позволяет сервисам находить друг друга внутри Docker-сети без использования жестко заданных IP-адресов.

### 3. Путь данных: от "запроса на обучение" до "модели в MinIO"
**Статус:** [IMPLEMENTED (in feature/training-worker)]  
**Детали:** 
1. **Запрос:** Пользователь отправляет `POST /train` в `orchestrator`.
2. **Регистрация:** `orchestrator` создает запись в таблице `jobs` со статусом `pending`.
3. **Опрос:** `training-worker` в бесконечном цикле `worker_loop` опрашивает БД.
4. **Захват:** Воркер находит задачу, обновляет её статус на `Running` (используя атомарный `SELECT ... FOR UPDATE SKIP LOCKED`).
5. **Подготовка:** Воркер скачивает датасет из MinIO в локальную папку `/tmp/{dataset_name}`.
6. **Обучение:** Воркер запускает внешний процесс обучения: `subprocess.run(["python", "pipelines/first_ml_baseline/train.py", ...])`.
7. **Логирование:** Скрипт `train.py` обучает модель, сохраняет артефакты локально и отправляет метрики/параметры в **MLflow**.
8. **Сбор:** Воркер находит соответствующий `run_id` в MLflow (через тег `job_id`), скачивает модель (`download_artifacts`).
9. **Загрузка:** Воркер переводит статус в `persisting`, загружает модель в **MinIO** и записывает метаданные в таблицу `trained_models`.
10. **Завершение:** Статус задачи обновляется на `succeeded`.

### 4. Как реализована очередь задач?
**Статус:** [IMPLEMENTED]  
**Детали:** Очередь реализована через **polling (опрос) таблицы `jobs` в PostgreSQL**. Использование `FOR UPDATE SKIP LOCKED` в `services/training_worker/db.py` позволяет масштабировать количество воркеров, обеспечивая конкурентный и безопасный захват задач.

### 5. Какие именно статусы есть у задачи?
**Статус:** [IMPLEMENTED]  
**Детали:** Реализована следующая цепочка состояний:
* `pending` (создана в `orchestrator`)
* `Running` (захвачена воркером)
* `persisting` (процесс загрузки артефактов в MinIO)
* `succeeded` (успешное завершение)
* `failed` (критическая ошибка в процессе выполнения)

### 6. Какие именно поля в таблице jobs или models являются ключевыми?
**Статус:** [IMPLEMENTED]  
**Детали:** Активно используются типы `JSONB` для хранения метаданных:
* **`jobs`**: `job_id` (PK), `dataset_name`, `dataset_id`, `status`.
* **`trained_models`**: `job_id` (FK), `model_name`, `model_version`, `model_path`, **`metrics` (JSONB)**, **`parameters` (JSONB)**.
* **`prediction_logs`**: **`input_data` (JSONB)**, **`prediction` (JSONB)**, `latency_ms`, `status`.

### 7. Как именно запускается код обучения?
**Статус:** [IMPLEMENTED]  
**Детали:** Запуск происходит через **`subprocess.run()`** в `services/training_worker/worker.py`. Это позволяет запускать обучение как отдельный Python-процесс, что упрощает управление ресурсами и обработку ошибок.

### 8. Как модель попадает из скрипта обучения в MinIO?
**Статус:** [IMPLEMENTED]  
**Детали:** 
1. Скрипт `train.py` сохраняет модель локально в `artifacts/`.
2. Воркер скачивает её из MLflow в локальный буфер.
3. Воркер использует `minio_client.py` для загрузки байтового потока (`io.BytesIO`) напрямую в MinIO через `put_object`.
*Примечание: Механизм проверки целостности (checksum) на данный момент **не реализован**.*

### 9. Как именно мы передаем параметры в MLflow?
**Статус:** [IMPLEMENTED]  
**Детали:** 
* **Запись:** Скрипт `train.py` использует `mlflow.log_param` для гиперпараметров и `mlflow.log_metrics` для метрик.
* **Связывание:** При запуске в MLflow записывается тег `tags.job_id = {job_id}`.
* **Поиск:** Воркер находит нужный запуск, используя `client.search_runs` с фильтром по этому тегу.

### 10. Как мы решаем проблему GIL при предсказаниях?
**Статус:** [IMPLEMENTED]  
**Детали:** В `services/inference-service/app.py` используется **`ProcessPoolExecutor`**. Предсказания выносятся в отдельные процессы, что позволяет эффективно использовать многоядерные системы и обходить ограничения Global Interpreter Lock (GIL).

### 11. Модель загружается в память при старте сервиса или при каждом запросе?
**Статус:** [IMPLEMENTED]  
**Детали:** Модель загружается **один раз при старте процесса** (через `initializer` в `ProcessPoolExecutor` в `inference-service/app.py`). Это минимизирует latency при выполнении запросов `/predict`.

### 12. Как входящий JSON превращается в DataFrame для Scikit-Learn?
**Статус:** [IMPLEMENTED]  
**Детали:** В `services/inference-service/predictor.py` используется `pd.DataFrame([input_data])`. Валидация структуры и типов данных обеспечивается на уровне **Pydantic-моделей** (`schemas.py`) до попадания данных в логику предсказания.

### 13. Что произойдет, если воркер крашнется во время обучения?
**Статус:** [NOT IMPLEMENTED]  
**Детали:** Если процесс воркера будет принудительно завершен (например, `SIGKILL`), задача останется в БД со статусом `Running`. В текущей реализации **отсутствует механизм Watchdog** для обнаружения таких "зависших" задач и их автоматического перезапуска.

### 14. Есть ли у нас автоматические повторы (retries)?
**Статус:** [NOT IMPLEMENTED]  
**Детали:** Логика автоматического повтора задач при сбоях внешних сервисов (MinIO, БД, MLflow) **не реализована**.

### 15. Что будет, если пользователь пришлет в API неверные данные?
**Статус:** [IMPLEMENTED]  
**Детали:** Система вернет ошибку **`422 Unprocessable Entity`**. Благодаря FastAPI и Pydantic, валидация входящего JSON происходит автоматически на уровне сетевого интерфейса, предотвращая попадание некорректных данных в бизнес-логику.
